# Agent Note: 本地存储用一张 JSON 文档表，字段级后写者胜，聊天存成消息树

Status: implemented

## Problem

角色卡和聊天记录已经能读进内存（[角色卡导入](../feature/2026-10-19-card-import.md)、[聊天记录导入](../feature/2026-10-19-st-chat-import.md)），需要存进本机 SQLite。约束：

- 以后要做两台设备的同步（[同步方案](../../proposed/architecture/2026-10-19-sync-e2e-cloudflare.md)）：同步只传改动，两边离线各改各的，合并后不能丢数据，合并结果和先后顺序无关。
- 角色卡里有大量各家前端的私有字段（[角色卡导入](../feature/2026-10-19-card-import.md) 要求全部保留），结构会随规格变。
- Windows 和 iOS 共用一套存储逻辑，逻辑要能在 Node 里直接测，不用开 App。
- App 端用的 `tauri-plugin-sql` 2.6.0 没有事务接口：每次 `execute` 都是单独的调用，`BEGIN` / `COMMIT` 不能保证落在同一个连接上。

## Decision

### 分层

- `packages/core/src/store/driver.ts`：`SqlDriver` 接口，只有 `execute(sql, params)` 和 `select(sql, params)`，参数是 `string | number | null`，占位符用 `?`。
- `packages/core/src/store/doc-store.ts`：`DocStore`，所有表结构、迁移、读写都在这里，用 TypeScript 写。
- App 端（`packages/app/src/db.ts`）把 `@tauri-apps/plugin-sql` 的 `Database` 包成 `SqlDriver`。Rust 端（`packages/app/src-tauri/src/lib.rs`）只注册插件，不写任何表结构。权限在 `capabilities/default.json` 里开了 `sql:default` 和 `sql:allow-execute`。
- 测试用 `packages/core/src/testing/node-sqlite.ts`，把 Node 自带的 `node:sqlite` 包成 `SqlDriver`。core 的正式代码不引用它（core 的 `tsconfig.json` 排除了 `src/testing`）。

### 一张文档表

```sql
CREATE TABLE IF NOT EXISTS docs (collection TEXT NOT NULL, id TEXT NOT NULL, data TEXT NOT NULL, clocks TEXT NOT NULL, deleted INTEGER NOT NULL DEFAULT 0, updated_at INTEGER NOT NULL, device_id TEXT NOT NULL, seq INTEGER NOT NULL, PRIMARY KEY (collection, id))
CREATE INDEX IF NOT EXISTS docs_seq ON docs (seq)
CREATE INDEX IF NOT EXISTS docs_chat ON docs (collection, json_extract(data, '$.chatId'))
```

- 每行是一份 JSON 文档，`collection` 区分种类（`characters`、`chats`、`messages`）。
- `clocks` 记每个字段最后一次修改的时钟 `[时间戳, 设备 id]`。
- 迁移靠 `PRAGMA user_version`：`MIGRATIONS` 数组里第 n 项执行完，`user_version` 设成 n。语句都写成 `IF NOT EXISTS`，中途失败重跑也不会报错。
- 不用 `WITHOUT ROWID`：试过加上以后，`EXPLAIN QUERY PLAN` 显示按 `chatId` 查消息走的是主键扫描，不走 `docs_chat` 索引。去掉以后走索引。`doc-store.test.ts` 里有一个测试专门检查查询计划。
- `list(collection, where)` 的字段名要匹配 `/^[A-Za-z_][A-Za-z0-9_]*$/`，因为字段名是拼进 `json_extract` 路径里的，值走参数。

### 字段级后写者胜

`packages/core/src/store/merge.ts`：

- 合并两份文档时，每个字段比较时钟：时间戳大的胜，时间戳相同比设备 id。合并满足交换律和结合律，同步时不用管收到的先后。
- 删除是给 `$deleted` 字段记一个时钟（墓碑），行不删。删没删只看 `$deleted` 自己的时钟：另一台设备改了别的字段不会让它复活，只有本机对已删文档再 `put`（显式恢复，`$deleted` 记上更新的时钟）才会复活。
- 本机时钟单调递增：取 `max(当前时间, 上次时间 + 1)`，`applyRemote` 收到远端文档时也把上次时间推到远端的最大时间之后。系统时间往回调也不会产生更小的时钟。
- `seq` 是本机写入的递增序号，`changesSince(seq)` 按它列出上次同步之后的改动，留给以后的上传。

### 写入

- 所有写操作排进一个串行队列（`serial`），同一个 `DocStore` 里不会有两个写操作交错。
- 没有事务，所以批量写入（导入聊天）用多行 `INSERT`，每批 500 行。一批是一条语句，SQLite 保证单条语句原子；批与批之间不原子，中途失败会留下前几批。
- `insertMany` 用来写全新文档（导入），`put` 读出旧文档再合并。

### 消息树

`packages/core/src/chat/tree.ts` 和 `repo.ts`：

- 每条消息有 `parentId`。同一个父消息下的多条消息是兄弟，既是左右滑动的备选回复，也是分支。角色卡的开场白和备用开场白是根上的兄弟（空白的跳过）。
- 聊天文档的 `leafId` 指向当前看到的最后一条，从它往上走到根就是界面上显示的那条路径。切换备选（`selectBranch`）就是把 `leafId` 改成那条兄弟下面最新的叶子。
- 兄弟按 `createdAt` 排，相同再按 id。
- **编辑消息原地改 `content`**，按字段级后写者胜合并。这改掉了 [同步方案](../../proposed/architecture/2026-10-19-sync-e2e-cloudflare.md) 里「编辑生成新版本」的写法，原因见下面的备选方案。重新生成回复是新增一条兄弟。
- 删除一条消息会把它整棵子树打上墓碑。如果当前 `leafId` 在被删的子树里，改指向剩下的最后一个兄弟下面最新的叶子；没有兄弟就指向父消息。
- 导入 ST 聊天（`importStChatToStore`）：每条 ST 消息的多条备选变成兄弟，选中的那条带上 `stExtra` 接着往下连。

### 设备 id

暂时存在 WebView 的 `localStorage` 里（`db.ts` 里有 `shortcut:` 注释）。清掉 WebView 数据会换一个新 id，现在只影响时钟比较时的平局判定；做同步之前要挪进数据库或系统安全存储。

## Alternatives considered

- **每种数据一张表（characters、chats、messages 各有列）** — 最强的理由：列有类型，SQL 能直接查、能加约束，SQLite 的常规用法。否掉的原因：角色卡要保留各家前端的私有字段，列固定不下来；同步要做字段级合并，每张表都得写一套合并和变更记录。一张文档表只写一次。需要查的字段用 `json_extract` 表达式索引（目前只有 `chatId`）。
- **在 SQL 里用递归 CTE 取当前路径** — 最强的理由：只取路径上的几条，不用把整段聊天读进内存。否掉的原因：同步时墓碑、分支要在内存里一起算，`buildTree` 本来就要整段读；开发者 203 条消息的真实聊天，整段读出加建树在 node:sqlite 上是 9 ms。聊天长到几万条再改。
- **用 Rust（rusqlite）写存储，前端通过 Tauri 命令调用** — 最强的理由：有真正的事务，性能更好，不受插件接口限制。否掉的原因：存储逻辑就得在 Rust 和以后的 Worker 端各写一遍；用 TypeScript 写在 core 里，Node 测试直接覆盖。代价是没有事务（见上面的分批写入）。
- **整条记录后写者胜** — 最强的理由：实现最简单，每行一个时钟。否掉的原因：一边改了角色名、一边改了描述，同步后会丢掉其中一边的改动。
- **编辑消息时生成新版本、不改原消息（同步方案原来的写法）** — 最强的理由：编辑历史全部保留，两边同时编辑同一条也都不丢。否掉的原因：新版本要么成为兄弟（界面上和重新生成的回复混在一起），要么要再加一层「版本」结构。字段级后写者胜下，两边同时编辑同一条只保留更晚那份，开发者一个人用两台设备，几乎不会同时编辑同一条消息。

## Consequences

- 收益：
  - 存储逻辑全在 core，Node 测试覆盖。`doc-store.test.ts` 13 个、`merge.test.ts` 5 个、`repo.test.ts` 8 个，覆盖合并的交换律和结合律、墓碑、两台设备离线各改后同步、1203 条文档分批写入、查询计划、消息树的分支切换和删除。
  - 2026-10-19 在 node:sqlite 上用真实数据试过：`Tavo_万象_1HNyS.jsonl` 的 203 条消息写入 41 ms，读出当前路径 9 ms，数据库 784 KB，`万象_v2.json` 存进去再读出来和原来完全一样。
  - 2026-10-19 在真 App（`tauri dev`）里试过：用 WebView2 的调试端口（`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`）通过 CDP 操作界面。导入卡片、导入聊天（203 条全显示）、新聊天、发消息、加分支后刷新页面，分支和切换都还在；数据库文件在 `%APPDATA%\io.github.luoye17.silue\silue.db`。同一次还查出 ST 预设文件被当成 V1 卡导入的问题，已修，见 [角色卡导入](../feature/2026-10-19-card-import.md)。
- 代价：
  - 批量写入不原子，导入中途失败会留下一部分消息。
  - JSON 文档没有数据库层面的类型约束，结构全靠 core 的代码保证。
  - 墓碑不清理，删掉的数据一直占空间。
- 还没做：同步上传下载、设备 id 挪出 `localStorage`、墓碑清理、`App.tsx` 里的界面只是临时的测试界面。
