# Agent Note: 本地优先，用户自己的 Cloudflare 做端到端加密同步

Status: proposed

## Problem

开发者在 Windows 和 iPhone 上都玩，同一段聊天要在两边接着聊。具体约束：

- 没有 VPS，也没有 NAS。
- 电脑关机时手机要照样能玩，所以不能让手机连电脑上的服务端。
- 开源以后，用户大多不会自己搭服务器。
- 数据里有 API Key 和很私密的 RP 内容，云上不能存明文。
- 开发者不想手动设置、输入同步密码。
- 两台设备可能各自离线聊了几条（比如手机网络断了），同步以后一条消息都不能丢。

## Proposal

### 数据归属

每台设备上的本地 SQLite 是唯一的主数据。云端只用来交换改动，不作为数据源头。没有配置同步时，App 完整可用。

### 云端组成（部署在每个用户自己的 Cloudflare 账号里）

- **Worker**：所有同步请求的唯一入口，用共享密钥鉴权。客户端不持有任何 R2 或 D1 的密钥：开源以后，写进客户端的密钥会被人翻出来。
- **D1**：存一张变更表，字段是 `id, table, updated_at, device_id, deleted, ciphertext`。客户端记住「上次同步到哪」，每次只拉这之后的变化。删除只打删除标记，不真删。
- **R2**：存头像、角色卡 PNG、背景图这类大文件，按内容哈希命名。客户端上传、下载都用 Worker 签发的预签名 URL（最长有效 7 天，https://developers.cloudflare.com/r2/api/s3/presigned-urls/ ）。
- **部署**：README 里放「一键部署到 Cloudflare」按钮，App 里有设置向导：填 Worker 地址，然后扫码配对。

免费额度（调研时查到的数字）：

| 服务 | 额度 | 来源 |
|---|---|---|
| Workers | 每天 10 万次请求 | https://developers.cloudflare.com/workers/platform/limits/ |
| D1 | 每天读 500 万行、写 10 万行，存储 5 GB | https://developers.cloudflare.com/d1/platform/pricing/ |
| R2 | 每月 10 GB 存储，100 万次 A 类操作、1000 万次 B 类操作，流出流量免费 | https://developers.cloudflare.com/r2/pricing/ |

### 冲突规则

- **聊天消息存成一棵树**：每条消息有全局唯一的 id，记着它回复的是哪一条（父消息 id）。左右滑动出来的多个回复是同一个父消息下的兄弟节点。编辑消息原地改内容、按字段后写者胜（原先写的是「编辑生成新版本」，存储层落地时改了，原因见 [本地存储](../../implemented/architecture/2026-10-19-doc-store.md)）。两台设备在同一个父消息下各自新增的消息，同步后就是两条分支，用分支和滑动的界面就能切换。
- **角色卡、设置、世界书这类数据**：按字段比较，更新时间新的那份胜出；更新时间相同时，比较 `device_id`。
- 一段聊天当前停在哪条分支，算作一个设置字段，按上面同样的规则处理。

### 端到端加密（不用输密码）

1. 第一台设备生成一把随机密钥，存进系统的安全存储（Windows 凭据管理器 / iOS 钥匙串）。用户看不到它，也不用记。
2. 加新设备时，已配对的设备显示一个二维码，新设备扫码拿到密钥。
3. 配对时生成一份「恢复密钥」，要求用户另外保存。所有设备都丢失或重装时，只有靠它才能解开云上的数据。
4. 上传前在设备上加密，D1 的 `ciphertext` 和 R2 里的文件都只有密文。API Key 加密后也一起同步。
5. Worker 的共享密钥只负责「谁能读写」，不能解开数据。

例外：后台代跑时，当前这一轮的提示词和 API Key 会以明文经过 Worker，见 [后台生成](../feature/2026-10-19-background-generation.md)。

## Alternatives considered

- **在开发者的 Windows 电脑上跑服务端，手机连它（ST 的做法）** — 最强的理由：只有一份数据，根本不存在冲突；生成在服务端跑，手机切后台也不会断。否掉的原因：电脑关机手机就不能玩；出门在外要装 Tailscale 之类的工具；开源用户也得自己搭服务端。
- **WebDAV（比如坚果云）当同步盘** — 最强的理由：国内用户常用，不需要部署任何东西。否掉的原因：开发者选了 Cloudflare。另外 WebDAV 只能存文件，增量同步要自己设计文件格式和锁；免费额度的请求频率限制也没查。
- **客户端拿着 R2 的 API token 直接读写** — 最强的理由：不用部署 Worker，少一个组件。否掉的原因：开源客户端里的密钥迟早被人拿走；没有 Worker，后台代跑也没地方运行。
- **用户手动设一个同步密码** — 最强的理由：实现最简单，忘了密码也只是云上那份打不开。否掉的原因：开发者明确不想设、也不想输密码。
- **CRDT（比如 Automerge、Yjs）** — 最强的理由：冲突能自动合并到字符级。否掉的原因：RP 数据主要是追加消息，树形存储已经能保证不丢；CRDT 的元数据开销大，也增加了 AI 写错的面积。

## Acceptance criteria

- 两台设备在同一个父消息下离线各发一条，联网同步后，两边都能看到两条分支，内容完全一致。
- 抓包和查看 D1 / R2 时只能看到密文。
- 删掉 App 重装，用恢复密钥能恢复全部数据；不用恢复密钥、只在已配对的设备上扫码，也能恢复。
- 不配置同步时，App 的所有功能照常可用。
- 一个人日常使用（每天几百条消息）不超出 Cloudflare 免费额度。

## Risks

- **时钟不准**：按更新时间判胜负，设备时间不准时，可能让旧的改动覆盖新的。聊天消息不受影响（树形存储只追加），只影响设置类数据。
- **恢复密钥弄丢**：所有设备都丢了、恢复密钥也没存，云上的数据就永远解不开。配对时要把这一点讲清楚。
- **免费额度变动**：Cloudflare 改了免费额度，同步可能需要付费。
- **Worker 共享密钥泄露**：别人能写入垃圾数据或删除数据，但解不开内容。需要能在 App 里重新生成共享密钥。
