# Agent Note: 长期记忆用分层前情回顾 + 状态表，第一版内置

Status: proposed

## Problem

开发者要求第一版的长期记忆就要好用。RP 一聊就是几百上千条，全部原文发给模型既贵又容易超出上下文；只发最近一段，模型又会忘掉早期的人物、约定和剧情。

另一个约束是缓存（见 [缓存排布](2026-10-19-prompt-cache-layout.md)）：记忆内容要是每轮都改写，提示词前面的部分就变了，缓存全部失效。

开发者自己在 Tavo 里写过一个记忆插件「万象记忆」（manifest `com.wanxiang.memory` v1.2.2），已经在实际使用，它做了这些事：

- 每条 AI 回复后，从卡片输出的 `<status>`、`<world>`、`<memo>`、`<npc>` 里解析出状态快照，按消息 id 存档。
- 每次生成前，把存档拼在本轮用户消息前面。
- 每 10 条回复写一章前情回顾，超过 12 章就把最早 6 章合并成一章。
- 把用户在括号里提过的长期要求整理成「永久规则」。
- 每轮都附上用户的偏好（喜欢 / 不介意 / 避开）。
- 每条回复后显示三个剧情灵感按钮。

## Proposal

### 记忆调研的结论（2026-10-19）

- 社区最受欢迎、和缓存最兼容的是分层总结：qvink MessageSummarize、Summaryception、ST-MemoryBooks 都是这一类。Summaryception 专门有一个 Prefix Cache 模式，攒够一批才刷新一次（https://github.com/mozophe/Extension-Summaryception ）。
- 向量检索会改动提示词前缀，ST 官方文档写明它和缓存只能二选一，并且「不保证改善记忆」（https://docs.sillytavern.app/extensions/chat-vectorization/ ）。
- MemDelta（https://arxiv.org/abs/2606.29914 ）在 LongMemEval-S 上的对比：原文检索 47.2%，全上下文 49.8%，差异不显著；只换 embedding 模型就能差 6.2 个百分点；让模型自己调工具管理记忆，得分 42%，比普通检索还低。
- 目前没有公认的 RP 长期记忆评测，各家的跑分都是自报的。

### 设计

1. **分层前情回顾**
   - 原文区超过阈值（初始值 2 万 token，实测后调整）时，把最早的一批原文一次性写成一章前情回顾，追加到记忆档案区，这批原文从提示词里移出。
   - 章节太多时，合并成更高一层的章节。
   - 每章记着自己覆盖了哪些消息 id。这些消息被编辑、删除或重新生成时，只把这一章作废重写。
   - 前情回顾只写已经发生的事实和用户做的决定，不写悬念和猜测。
2. **状态表**：角色当前状态、人物关系、没收尾的剧情线、关键物品，放在动态尾部。来源二选一：
   - 卡片自己会输出状态栏的（比如万象卡的 `<status>`、`<npc>`、`<memo>`），直接解析它，不再额外调用模型。解析哪些标签由用户配置，第一版只保证万象卡的格式能用。
   - 卡片不输出状态栏的，由辅助模型每隔 N 轮更新一次。
   - 每段聊天可以单独关掉状态表，默认开。
3. **永久规则**：写前情回顾时，顺便把用户在括号里说过的长期要求整理出来，放进不变区。
4. **偏好**：喜欢 / 不介意 / 避开三栏，放进不变区。全局有一份，每段聊天可以单独改。
5. **剧情灵感**：每条回复后，调一次辅助模型生成三个剧情走向按钮，点一下直接发送。默认开，可以关。
6. **找回旧细节**：用关键词检索（BM25）在原文里搜，搜到的片段放进动态尾部。embedding 检索以后做成可选功能。
7. **回退一致性**：组装提示词时，只使用最后一条用户消息之前的状态快照。这样重新生成或回退时，不会读到已经作废的那条回复里的状态。
8. **辅助模型**：写前情回顾、更新状态表、生成剧情灵感都用它。默认和主模型相同，可以单独指定一个便宜的模型。
9. **可见、可改、可撤销**：前情回顾自动生效，不弹窗确认。记忆面板里能看到每一章、每张状态表，可以修改，也可以撤销。

## Alternatives considered

- **向量检索为主（ST Vector Storage、RisuAI HypaMemory 那一类）** — 最强的理由：能按意思找回很久以前的细节，不靠关键词碰运气。否掉的原因：检索结果每轮都不一样，放在前面会让缓存失效；MemDelta 的结果显示它比全上下文没有显著提升，而且很依赖 embedding 模型选得好不好；iOS 上本地跑 embedding 的速度也没核实。所以留作以后的可选功能。
- **让模型自己调工具管理记忆（MemGPT / Letta 那一类）** — 最强的理由：最灵活，模型自己决定记什么、忘什么。否掉的原因：MemDelta 里这类方法得分最低；多轮工具调用很慢；四家 API 的工具调用行为不一致；工具结果插在对话中间，缓存也难控制。
- **知识图谱（Zep / Graphiti）** — 最强的理由：自报的评测分数高，人物关系的表达最自然。否掉的原因：写入成本高、系统复杂，分数是厂商自报的；第一版不做。
- **每次写完前情回顾弹窗让用户确认** — 最强的理由：ST 文档和 MemoryBooks 的指南都提醒，自动总结会漏细节、甚至编造。否掉的原因：每次都弹窗会打断 RP。改成自动生效，同时可以随时查看和撤销。
- **保留万象记忆插件，不做内置** — 最强的理由：它已经能用，开发者也熟悉。否掉的原因：它依赖 Tavo 的插件接口，Silue 第一版不提供插件系统（见 [角色卡渲染](2026-10-19-card-html-sandbox.md)）；而且它把存档拼在用户消息里、每轮都变，享受不到不变区的缓存。

## Acceptance criteria

- 拿开发者导出的 `Tavo_万象_1HNyS.jsonl`（203 条消息）导入后，从第 1 条开始重放，生成的前情回顾覆盖全部 AI 回复，每章覆盖的消息 id 连续、没有遗漏。
- 编辑一条已经被写进前情回顾的消息后，只有包含它的那一章被标记为作废并重写，其他章节不变。
- 在原文区触发压缩之前，连续两轮的提示词第 1、2 段逐字相同（用标准答案测试检查）。
- 万象卡的 `<status>` 状态栏能被正确解析成状态表；对这条消息重新生成后，状态表回到上一条的快照。

## Risks

- **前情回顾出错**：总结模型会漏细节或编造。缓解办法是可以随时查看、修改、撤销，以及前情回顾只写事实。
- **状态栏格式各不相同**：每张卡的状态栏写法都不一样，通用的解析做不到，只能让用户配置；第一版只保证万象卡。
- **辅助模型费用**：开着剧情灵感时，每条回复都要多调用一次模型；写前情回顾也会额外花钱。设置里要写清楚。
- **阈值选得不好**：压缩得太频繁，缓存经常失效；压缩得太少，上下文太长、成本高。需要用真实长对话实测来定。
